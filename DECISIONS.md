# Decisions

Settled architectural and product decisions. Do not reopen without new
information that directly invalidates a stated reason.

| ID | Decision | Chosen | Rejected | Reason | Date | Status |
|---|---|---|---|---|---|---|
| D-001 | Edge thesis | Volatility selling as the backbone; directional debit spreads only on high-conviction signals | Pure directional long options; pure trend following | Long options fight theta and need both direction and timing correct; the implied-over-realized premium is documented and persistent, giving positive expectancy over many trades without requiring a directional forecast | 2026-09-02 | active |
| D-002 | Structure risk profile | Defined-risk only (vertical spreads, iron condors) | Naked short puts/calls, ratio spreads | Undefined-risk short premium makes the drawdown guardrail unenforceable — max loss must be computable at order time for `risk.evaluate()` to size and veto | 2026-09-02 | active |
| D-003 | Optimization target | Consistent expectancy with hard drawdown control, not maximum return over the judging window | Maximizing P&L over the hackathon week | Options P&L over a one-week window is dominated by noise; a system tuned to win a sprint reads as gambling to judges and does not survive past it | 2026-09-02 | active |
| D-004 | LLM boundary | LLM used at exactly two points: regime labeling and structure construction. Signal computation, sizing, management triggers, and risk enforcement are deterministic Python | LLM-driven end-to-end loop; fully rule-based system with no LLM | An end-to-end LLM loop burns tokens on plumbing and introduces variance into arithmetic that is exactly computable; a fully rule-based system forfeits the agentic originality the rubric rewards. Splitting on "judgment vs correctness" gets both | 2026-09-02 | active |
| D-005 | Risk agent implementation | Fully deterministic, no LLM, veto authority over every order | LLM risk reviewer | A risk check that can hallucinate is not a risk check. Determinism also makes the veto log reproducible evidence for judging | 2026-09-02 | active |
| D-006 | Regime agent implementation | Deterministic feature computation, then LLM assigns a label from a fixed enum **and** may deviate from the mechanical read when it states a reason; rationale is logged | Pure quantitative classifier; unconstrained LLM classification | Fixed enum bounds the blast radius of a bad label while the deviation latitude is where the LLM actually adds value over a threshold rule. Free-form classification would let it invent regimes the eligibility map does not cover | 2026-09-02 | active |
| D-007 | Agent decomposition | Four specialists under a supervisor: regime, signal, strategy-construction, risk | Collapsing signal into strategy-construction | Signal is deterministic and runs on a different cadence than structure construction; merging them would force LLM invocation on every scan instead of only when a signal fires | 2026-09-02 | active |
| D-008 | Execution path | Alpaca **MCP server** is the sole path for orders, positions, and account state; `alpaca-py` REST is used only for bulk market data | Routing all Alpaca traffic through MCP; using the SDK for everything | The rubric explicitly credits MCP/CLI usage and execution is where judges look; routing per-symbol chain snapshots through MCP round-trips would be wasteful on a free-tier VM with no benefit | 2026-09-02 | active |
| D-009 | Inference provider | Groq free tier, behind a model-agnostic client interface | Local Ollama; paid frontier API | Zero budget rules out paid APIs. Local was rejected on hardware: the available laptop runs ~8B at 5-10 tok/s and is not always powered on, which disqualifies it for a system that must run through market hours | 2026-09-02 | active |
| D-010 | Inference failure behavior | Degrade to hold-and-manage: existing positions continue under deterministic management rules, no new entries opened | Falling back to a local small model; halting entirely | A weak fallback model constructing options orders is a worse failure than not trading; halting entirely would abandon open positions to expiry unmanaged. Management rules are deterministic and need no LLM | 2026-09-02 | active |
| D-012 | Persistence | SQLite, single file, WAL mode | Supabase Postgres; Postgres on the VM | Single-process system with no concurrent writers and no need for network access. A network DB adds a failure mode inside the trading loop for zero benefit. Supabase is used elsewhere in the owner's stack but that is not a reason to add a network hop here | 2026-09-02 | active |
| D-013 | State ownership | Alpaca is authoritative for positions and cash; SQLite is authoritative for entry credit, management plan, IV history, and high-water mark; the process holds no authoritative state | Keeping position management context in process memory | In-memory state is destroyed by redeploy, and the system will be redeployed repeatedly during the build. Reconstructing from Alpaca + SQLite on every boot makes restart a non-event | 2026-09-02 | active |
| D-014 | Logging vs state | Two separate structures: append-only `decision_log` for history and reasoning, mutable `positions` table for current facts | Reconstructing current state by replaying the decision log | Replaying a log to answer "how do I manage this open condor" is fragile and slow; a current-state row is a single read. The log remains as the fallback reconstruction path if the state table disagrees with Alpaca | 2026-09-02 | active |
| D-015 | IV history | System accumulates its own ATM IV observations into `iv_history` every scan | Querying historical IV from Alpaca on demand | Alpaca's option chain endpoint is a live snapshot with no historical lookup, so IV rank is not obtainable from the API at all. It must be self-accumulated | 2026-09-02 | active |
| D-016 | IV cold start | Backfill `iv_history` by inverting Black-Scholes on ~30 trading days of Alpaca historical option bars before first run | Waiting for live observations to accumulate; bridging with realized volatility only | Without a seed, IV rank is undefined for weeks and the entire vol-richness signal is blind during the period the system is being evaluated. Alpaca has option bars back to Feb 2024, which is enough to seed | 2026-09-02 | active |
| D-017 | Backfill and live IV share one table and format | Single `iv_history` table with a `source` column; ranking code is source-agnostic | Separate tables or a cutover from seeded to live data | One schema and one ranking function removes an entire class of bugs; the seed ages out of the trailing window naturally with no cutover event | 2026-09-02 | active |
| D-018 | Backtesting | Not built | Full backtest harness; replaying LLM decisions | Only the deterministic layer is cleanly backtestable, the options leg requires reconstructing contract symbols with no historical chain, and the LLM layer is non-deterministic. Live paper trading produces real fills and is what the rubric scores | 2026-09-02 | active |
| D-019 | Universe | Seven liquid ETFs: SPY, QQQ, IWM, GLD, TLT, XLE, HYG. Config-driven | S&P 500 constituents; mega-cap single names | Most single names have wide options spreads that consume the premium edge on entry and exit, and carry earnings gap risk. These seven span equity beta, metals, duration, energy, and credit — five distinct risk drivers rather than one bet held seven times | 2026-09-02 | active |
| D-020 | XLE over USO for energy | XLE | USO | Deeper options chain and no futures-roll distortion in the underlying | 2026-09-02 | active |
| D-021 | DTE window | 7-14 DTE, config-driven | 30-45 DTE | Standard 30-45 DTE premium selling will not realize P&L inside the evaluation window. Shorter DTE cycles positions fast enough to produce a visible equity curve; the value is config so it can be widened after | 2026-09-02 | active |
| D-022 | Order pricing under delayed quotes | Limit orders stepped through a price ladder from delayed mid toward market, cancelled if unfilled at the last rung | Market orders; single limit at mid | The free indicative feed is delayed 15 minutes, so mid is stale by construction. Market orders on multi-leg options spreads invite bad fills; a single stale-mid limit will often not fill at all | 2026-09-02 | active |
| D-023 | Demo/dashboard artifact | Not built for v1 | Static HTML equity-curve and trade-log renderer | Explicitly declined during scoping. `decision_log` and `equity_curve` hold the underlying data if it is added later | 2026-09-02 | active |
| D-024 | Risk-free rate for BS inversion | Constant, config value `RISK_FREE_RATE`, default 0.04 | Live treasury curve lookup | IV output is consumed only for percentile ranking within a symbol, not for pricing. A constant-rate bias is near-uniform across observations of the same symbol and cancels in the ranking | 2026-09-02 | active |
| D-025 | Dividends in BS inversion | Ignored; documented as accepted systematic bias | Forward-price adjustment using dividend estimates | Same reason as D-024 — the bias is roughly constant per symbol and cancels in a within-symbol percentile. Revisit only if IV values are ever used for absolute pricing decisions | 2026-09-02 | active |
| D-026 | BUILD.md phase framing | Dependency-ordered task slices with acceptance criteria, no time estimates or calendar labels | Day-by-day or hour-budgeted plan | A phase is complete when its criteria pass, not when a clock expires. Time labels go stale immediately and invite shipping incomplete slices | 2026-09-02 | active |
| D-027 | Multi-leg order capability | Spreads and condors are submitted as single atomic multi-leg orders through the Alpaca MCP server | Legging into each spread with sequential single-leg orders | Confirmed by the project owner that the MCP server supports multi-leg submission. Sequential legging was the only alternative and is unacceptable: a partially-legged spread is an undefined-risk position, which breaks D-002 and makes the drawdown tiers in docs/RISK.md unenforceable | 2026-09-02 | active |
| D-028 | Q-001 resolution: MCP tool names and argument schemas | `mcp_client.REQUIRED_TOOLS` maps to the tool names of `alpacahq/alpaca-mcp-server` v2 (`get_account_info`, `get_all_positions`, `get_orders`, `place_option_order`, `cancel_order_by_id`, `close_position`). Multi-leg orders use `order_class="mleg"`, per-leg `{symbol, ratio_qty, side, position_intent}`, and a single signed `limit_price` where **positive = debit/cost, negative = credit/proceeds** — the opposite sign of this system's own `net_credit` convention, so `mcp_client.place_mleg_order` negates it internally. Positions carry an unsigned `qty` + `side` ("long"/"short") rather than a signed qty, and P&L is `unrealized_pl` not `unrealized_pnl`; orders carry `id` not `order_id`, and a multi-leg order's per-leg symbols live under `legs`, not a top-level `symbols` list. Launch via `uvx alpaca-mcp-server` (env: `ALPACA_API_KEY`, `ALPACA_SECRET_KEY`; `ALPACA_PAPER_TRADE` optional, defaults true) | Guessing a schema and discovering the sign convention wrong on a live order (Q-001's own stated risk: "either fill instantly at a bad price or never fill") | Read directly from the vendor's published source — `README.md`'s tool catalog and `src/alpaca_mcp_server/overrides.py`'s `place_option_order` signature in `alpacahq/alpaca-mcp-server` (fetched 2026-09-03) — rather than inferred from Alpaca's REST docs, which Q-001 explicitly warned might not match the MCP surface. **Updated 2026-09-03, same day:** connected to the real server with real (now-rotated) paper-account credentials and ran `mcp_client.connect()` for real — `uvx alpaca-mcp-server` started, `list_tools()` returned exactly the 72 tools expected, and `assert_required_tools()` passed with zero missing tools; `REQUIRED_TOOLS`'s six mappings are confirmed correct against a live server, not just source-read. The one thing NOT verified live is a real order/account-data round trip: this session's network egress policy blocks both `paper-api.alpaca.markets` and `api.groq.com` (confirmed via two separate 403s from the sandbox's proxy, not a bug in this codebase) once a tool call actually needs to reach Alpaca's REST backend, so `get_account_info` couldn't complete. **Before Phase 7's acceptance criteria are considered met, place one small real order (from an environment that can actually reach Alpaca) and confirm the fill price and sign land where expected** — narrowed now from "confirm the schema" (done) to "confirm one real transaction" | 2026-09-03 | active |
| — | *(continuation of D-028, 2026-09-03, project owner's own machine)* | First real tool call (`get_all_positions`, zero-position paper account) revealed one more layer this system's source-reading pass missed: the server wraps every tool's actual return value in a security envelope, `{"_alpaca_mcp_security": {"trust": "untrusted_tool_output", ...}, "data": <payload>}` — a deliberate guard against prompt injection via API data (the envelope's own `instructions` field tells the calling model not to follow anything embedded in the data). `mcp_client._unwrap()` didn't know to peel this off, so `get_positions()` crashed trying to iterate the envelope dict directly. Second live call (`get_account_info`, same session) then exposed a subtlety in that same envelope: an **object**-shaped payload (the account fields) sits directly under `data`, but an **array**-shaped payload (the positions list) sits one level deeper under `data.result` — the first fix only handled the array case and silently fell back to returning the whole envelope for the object case, so `get_account()` then `KeyError`'d on `equity`. Fixed once, correctly, in `_unwrap`: object payloads returned directly, array payloads unwrapped from `result`, with regression tests using both exact captured payloads (`tests/test_mcp_client.py`) rather than one guessed generalization from a single example. This is exactly what D-028's own caveat anticipated — vendor-source-reading gets close but a live call still surfaces things a static read doesn't, sometimes more than once. | 2026-09-03 | active |
| D-029 | Host | Personal Windows machine via WSL2 (Ubuntu), run in the foreground and started/stopped around market hours (not a persistent daemon) | GCP e2-micro / Oracle Always Free (D-011, superseded); a spare Pi or laptop | D-011's premise — an always-on VM funded by a free tier — assumed a card was available for identity verification. The project owner has no card of any kind (not even debit), which every major free-tier provider checked (GCP, Oracle, Fly.io) now requires regardless of intent to charge; the remaining "no card at all" options are low-trust free-VPS listicle sites, unacceptable for a host holding live Alpaca/Groq credentials. No spare always-on hardware is available either — only the owner's daily-driver Windows machine. Accepted tradeoff, made explicitly rather than silently: this is no longer truly "unattended" (CLAUDE.md's own framing) during hours the machine is off; D-013's reconcile-on-boot design means restarting is still safe, but an open position is unmanaged (no take-profit/stop/halt) for however long the machine is off. Owner's call, made with that tradeoff stated plainly | 2026-09-04 | active |
| D-030 | Stock data feed | `DataFeed.IEX` set explicitly on `StockBarsRequest`/`StockLatestTradeRequest`; `OptionsFeed.INDICATIVE` (the enum, not a raw string) on `OptionChainRequest` | alpaca-py's unset default (which resolved to SIP) | First live `iv.ensure_seeded()` run 403'd: `{"message":"subscription does not permit querying recent SIP data"}` — a free/paper account can't query recent SIP data, only IEX (free, real-time-ish) or SIP delayed/historical. docs/DATA.md already specified `feed=indicative` for the options chain (as a string, which happened to validate but wasn't the proper enum), but `fetch_daily_bars`/`fetch_latest_price` never set a stock feed at all, silently inheriting whatever alpaca-py defaults to. Not caught by any test since it needs a real account to surface — exactly the kind of gap D-028's own note anticipated | 2026-09-04 | active |
